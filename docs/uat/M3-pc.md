## 測試方法與限制

- 開始前與結束後:解除該 origin 的 service worker、刪除 Cache Storage、清空 `localStorage` / `sessionStorage`(結束後確認 0 筆 / 0 個 / 0 個)。
- 以真實使用者的方式點擊畫面上的按鈕;只有下列兩處用 devtools 輔助:
  - **選檔**:作業系統的檔案對話框無法自動化,以 `DataTransfer` 設定 `input.files` 後觸發 `change`(與真實選檔進入同一段程式)。
  - **清除資料**與**把起始日改到 14 天前**:app 沒有「清除資料」功能(設計如此),以 devtools 清空 `localStorage` / 修改 `program.startDate`、`meta.lastExportAt` 後重新整理。
- 匯出的下載:確認 app 以 `<a download>` 觸發下載、檔名與內容正確;內建瀏覽器的下載實際存到哪裡無法從這裡驗證(電腦「下載」資料夾內沒有出現檔案,判斷為內建瀏覽器的下載處理方式,不是 app 問題)。

## UX 建議(不阻擋,供 PM 排入後續里程碑)

1. **匯入預覽看不到「目前的資料」**(建議優先)。覆蓋前只顯示備份檔的內容,使用者無法判斷這份備份是否比手機上的舊。建議在覆蓋模式加一列「目前資料:N 天紀錄」,或在備份的紀錄天數少於目前資料時多一句提醒,避免誤用舊備份蓋掉新資料。
2. **「覆蓋前會自動另存一份目前的資料」但使用者看不到也用不到那份資料**。這份自動備份只存在 `localStorage`,app 內沒有入口可以還原,文字容易讓人以為可以「復原」。建議:未來加「還原匯入前的資料」,或把文字改成較不會誤解的說法。
3. **引導頁的「從備份還原」在最下面**。換手機的使用者要先捲過整個習慣清單才看得到。建議把「已經有備份?」移到頁首附近,或在頁首放一個小連結。
4. **錯誤視窗有兩個關閉按鈕且名稱不同**:標題列是「取消」、底部是「關閉」。錯誤訊息沒有可「取消」的動作,建議標題列也用「關閉」或拿掉。
5. **「持久化儲存」是技術用語**。建議改成「資料保護」或「防止瀏覽器自動清除」之類的說法;「未啟用」時的說明可以直接接一句「請定期匯出備份」。
6. **從提醒跳到設定頁後,「匯出備份」雖然有焦點但看不太出來**。可以考慮短暫高亮該按鈕,讓使用者知道下一步按哪裡。
